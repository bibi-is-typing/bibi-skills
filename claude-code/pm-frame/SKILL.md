# PM 프레임: 요청에서 결정까지

한비가 좋은 질문과 근거로 판단하고 그 이유를 결정문에 남기도록 돕는다. 기존에 합의한 결정과 실행 범위를 존중한다. 여섯 단계는 사고의 순서이며, 모든 요청에 여섯 번의 인터뷰를 강제하는 절차가 아니다.

## 모드 선택

- **인터뷰**: 새 기획을 함께 생각하거나 PM 프레임 질문을 요청한 경우. 기존 맥락으로 채울 수 없는 첫 단계부터 질문 하나씩 진행한다.
- **점검**: 기획서·덱·설계서를 검토하는 경우. 먼저 6단계 기준으로 강점·빈칸·결정에 미치는 영향을 제시한다. 자료에 있는 답을 다시 묻지 않는다.
- **결정문**: 결정문이나 초안을 요청한 경우. 확보한 재료로 먼저 작성하고 미정인 항목을 표시한다. 사용자가 인터뷰를 원하지 않으면 초안 작성을 멈추고 인터뷰를 시작하지 않는다.

인터뷰 요청이 명확하면 질문으로 시작한다. 자료 검토나 초안 요청이면 결과를 먼저 만든다. 단순 구현 요청에는 이 스킬을 자동 적용하지 않으며, 사용자가 `/pm-frame`을 명시했다면 그 범위에서 프레임을 사용한다.

## 6단계

| 단계 | 판단할 질문 | 산출물 |
|---|---|---|
| 1 | 무엇이 진짜 문제인가 | 문제 한 문장, 문제의 주인, 문제 사다리 |
| 2 | 무엇을 근거로 판단하나 | 사실·해석·추측 표, 위험한 가정과 확인 방법 |
| 3 | 왜 지금 풀어야 하나 | 지연 비용, 지금·다음·하지 않을 범위 |
| 4 | 왜 이 해결책인가 | 무행동을 포함한 대안 비교, 선택 이유, 반증·되돌림 |
| 5 | 무엇이 바뀌면 성공인가 | 선행·후행·가드레일 지표, 기준선, 최소 검증 |
| 6 | 무엇을 결정하나 | 결정문, 실행·실험 계획, 담당·기한·재검토 |

현재 다루는 단계의 목적·핵심 질문·통과 기준은 [단계별 진행](references/stages.md)을 읽는다. 점검 모드에서는 여섯 단계 전체를 대조한다. 해결책을 비교할 때는 현행 유지와 실질적으로 다른 대안을 고려한다. 이미 정한 제약 때문에 선택지가 제한되면 그 이유를 남긴다.

## 맥락과 근거

현재 대화, 사용자가 지정한 문서, 현재 프로젝트의 관련 결정과 제약부터 읽는다. 사용할 수 있는 연결 도구가 있으면 필요한 맥락을 좁혀 찾는다. 다른 채팅·메모리·볼트에 자동 접근할 수 있다고 가정하지 않는다. 관련 자료를 찾지 못하면 그 부분을 미정으로 두고 계속한다.

원본 프레임에 나오는 `audience-map.md`와 `pm-identity.md`는 선택적 맥락이다. 현재 프로젝트나 사용자가 제공한 위치에 있을 때만 참고한다. 특정 볼트 경로를 필수 의존성으로 두거나 무관한 개인 파일을 탐색하지 않는다. 과거 문서의 목표·조직 상황은 현재 사용자 설명과 대조한다.

주장에 다음 꼬리표를 붙인다. 출처가 있다는 것과 내용이 검증됐다는 것을 구분한다.

- `[사실 · 데이터]`: 측정 출처·기간·단위가 있고 재확인 가능한 숫자. 사용자가 전달한 수치만 있으면 `사용자 제공, 원자료 미확인`을 함께 적는다.
- `[사실 · 현장 진술 · 직접/전언]`: 누가 무엇을 말했다는 근거. 직접 경험인지 전해 들은 것인지 구분한다. 발언 내용 자체가 사실로 입증된 것은 아니다.
- `[해석]`: 사실로부터 추론한 내용.
- `[추측]`: 아직 확인하지 못한 내용. 검증할 가정으로 옮긴다.
- `[해법 후보]`: 해결책 제안. 4단계 비교 대상으로 보관한다.

핵심 가정은 틀렸을 때 손실과 확인 비용으로 정렬한다. 근거 없는 숫자, 인터뷰 내용, 담당자의 약속을 만들어 빈칸을 채우지 않는다.

## 인터뷰 진행

1. 한 번에 핵심 질문 하나를 묻고, 왜 필요한지 한 줄로 설명한다. Claude Code에서 사용자 질문 도구를 쓸 수 있으면 사용하되 현재 권한과 모드 제약을 따른다. 도구가 없으면 일반 응답 끝에 질문 하나를 둔다.
2. 답을 받으면 꼬리표와 관찰을 짧게 정리하고 다음 질문으로 이어간다. 이미 받은 답은 재사용한다. 기술 선택은 무엇·이유·작업량과 의존성·사용자 및 운영 영향을 이해할 수 있게 설명한다.
3. 해법부터 시작한 인터뷰에서는 그 해법이 누구의 무엇을 바꾸는지 묻는다. 이미 승인된 실행을 다시 문제 정의부터 시작하게 하지 않는다.
4. 모르는 내용은 확인할 가정, 확인 방법, 담당·기한으로 남긴다. 담당·기한도 모르면 `미정`이라고 쓴다.
5. 단계별로 `확인됨 / 가정으로 진행 / 미정`을 구분한다. 근거가 없는데 통과했다고 쓰지 않는다. 그 단계에서 가능한 산출물을 정리하고, 나머지 작업은 계속할 수 있다. 추가 답이 필요한 인터뷰 질문은 답을 기다린다.

한국어는 비유·장식적 대비·문두 접속사 뒤 쉼표·em dash를 줄이고 직접 쓴다. 실제 불확실성은 명확히 남긴다. 결정문을 다듬을 때 `korean-writing`이 설치돼 있으면 해당 스킬을 사용할 수 있다. 없으면 사실·가정·독자·문체를 직접 점검하며 계속한다.

## 공유 범위와 PM 역할

문제 사다리의 회사 사정, 인사, 투자 등 민감한 상위층은 내부 메모로 구분한다. 공유판에는 정해진 독자와 전달 범위에 필요한 정보만 담는다. 이미 정해진 공개 범위를 단계마다 다시 묻지 않는다. 공개 범위가 불명확하면 내부 초안부터 만들고 공유판에 필요한 범위만 확인한다. 작성과 저장은 외부 발송으로 이어지지 않는다.

한비의 원본 프레임은 커머스 문제를 시스템·데이터·AI로 풀고 매출 지표로 결과를 책임지는 PM 역할을 지향한다. 현재 목표가 다르면 현재 맥락을 따른다. 5·6단계에서 기준선 측정 설계, 결과 보고 담당, 한비가 맡는 일과 위임할 일, `문제 → 조율 → 출시 → 지표`의 빈칸을 점검한다. PM 역할과 개인 경력 메모는 내부판에만 남긴다. 역할·경험 목록을 제공받지 못했으면 일치 여부를 지어내지 않는다.

## 결정문과 저장

6단계나 결정문 모드에서 [결정문 양식](references/decision-doc-template.md)을 읽는다. 제안은 `결정 제안`, 미확정 문서는 `초안`으로 표시한다. 실제로 확정된 결정만 확정 상태로 쓰고, 사용자에게 주어진 결정권을 넘겨 짐작하지 않는다. 내용만으로 충분한 짧은 요청에는 양식 전체를 억지로 채우지 않는다.

완성된 결정문은 사용자가 지정한 위치에 저장한다. 위치를 지정하지 않았다면 현재 프로젝트의 문서 관례를 따른다. 프로젝트 문서 위치가 없으면 현재 작업 폴더에 저장한다. 파일명은 `decision-<주제>-<YYYY-MM-DD>.md`로 하고 날짜는 사용자 시간대의 날짜를 쓴다. 저장할 파일시스템이 없거나 사용자가 채팅 결과만 원하면 본문을 채팅으로 제공한다. 기존 파일은 사용자 요청에 맞게 갱신하고 무관한 파일을 덮어쓰지 않는다.

공유판은 요청받았을 때 기밀 내용과 PM 역할 메모를 제거해 따로 작성한다. 내부판 링크·인용·부록에 같은 정보가 남지 않았는지도 확인한다.
